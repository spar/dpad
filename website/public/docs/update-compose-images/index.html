Update Compose images safely

Updated 28 November 2026

The usual way to update a Compose project is two commands in its folder. dpad runs the same two commands for one project or all of them, shows you what it will do first, and tells you what changed.

The manual way

$ cd ~/stacks/shop
$ docker compose pull
$ docker compose up -d

pull downloads newer images for the tags in your Compose file. up -d then recreates only the services whose image changed and leaves the rest running. Repeat for every project, and read the output to see which ones actually changed.

With dpad

  1. Open dp and press 4 for Projects.
  2. Press u on a project to update it, or U to update every project on this daemon, including stopped ones and ones hidden by your filter.
  3. Read the preview. Each project says ready or why it is blocked. enter on a row shows the host it will run on, the working directory, Compose files, env files, services and image tags.
  4. Press y.

Each project runs docker compose pull --include-deps, then up -d --no-build --pull never only if the pull worked. Projects run one at a time, and dpad reads each project's configuration again before every step: if it no longer matches the preview, that project stops with a message and nothing is pulled or recreated for it. A failed project doesn't stop the others.

Watching it run

Progress opens straight away. With several projects, the top half lists each one with its step and elapsed time, and the bottom half shows the active project like docker compose pull does: one row per image with its layers and bytes. l switches to the raw log, [ and ] look at another project, and tab shows the summary.

When it finishes, every project has a result: updated, N recreated, already up to date, or failed: with Compose's error. esc during the run cancels the remaining work.

What it doesn't do

  • It uses the tags already in your Compose files. To move from postgres:16 to postgres:17, edit the file first; enter after an edit goes straight to this preview.
  • It doesn't build images, run down, remove volumes or prune old images. Use prune afterwards to clean up.

Where Compose runs

dpad finds each project's folder and files from the labels Compose puts on its containers, so a project needs at least one container, running or stopped. When the files are on this machine, Compose runs here against the current daemon. On an ssh:// daemon whose files are on the server, Compose runs on the server in the project's folder; the preview says which, and h switches when both machines have the files. Remote runs need a POSIX shell, Compose v2 and key or agent SSH authentication.

Projects started by a wrapper script

If a project's Compose file needs a variable that a script exported when it first ran Compose, Docker didn't record it. dpad looks for the value in the project's containers and uses it when they all agree, and the preview says so. When it can't, the project is blocked with Compose's hint, and you can set the value in config.yaml:

composeProjects:
  my-project:          # Compose project name
    env:
      STACK_NAME: production
