Run dp on your laptop and point it at the server. The terminal UI draws locally and only Docker data travels over SSH, so moving through lists never waits on the network.

$DOCKER_HOST=ssh://me@server dp

That is all it takes when you can already ssh me@server and your user on the server can reach the Docker socket.

Why not run dp inside an SSH session?

You can: install dp on the server and run it there. But then every keypress makes a round trip over SSH before the screen changes. With DOCKER_HOST=ssh:// the UI runs on your machine, list navigation is instant, and data loads happen in the background. dp also batches event and log redraws when it detects it is running inside SSH, but running it locally is still smoother.

Before you start

  • SSH access. Your ~/.ssh/config, agent and known hosts all apply, so a host alias like ssh://prod works. Password and host-key prompts appear before the UI opens.
  • Socket access on the server. For a normal (rootful) daemon your server user needs access to /var/run/docker.sock, usually by being in the docker group.
  • Key or agent authentication if you want dp to reconnect by itself after a dropped connection. It never prompts again once the UI is open.
  • The docker CLI on your laptop for shells (e) and passthrough commands such as dp exec. On macOS, brew install docker is enough; you don't need Docker Desktop for a remote daemon.

On Windows, set the endpoint in PowerShell with $env:DOCKER_HOST = "ssh://me@server" and then run dp.

Save the server as a Docker context

Typing DOCKER_HOST every time gets old. A Docker context remembers the endpoint for both docker and dp:

$ docker context create home --docker host=ssh://me@server
$ docker context use home
$ dp

With several servers saved, press c inside dp to switch between them without leaving the UI. That choice lasts for the session and doesn't change the Docker CLI's current context. See Docker contexts.

Rootless Docker or another socket path

Append the absolute socket path to the SSH address:

$ DOCKER_HOST=ssh://me@server/run/user/1000/docker.sock dp

Replace 1000 with the remote user's UID (ssh me@server id -u) and make sure their rootless daemon is running. Rootless Docker doesn't need the docker group. Use the real path: ~ and shell variables are not expanded on the remote side. The same address works in docker context create.

What happens on the wire

dp starts one ssh process that forwards a private local socket to the server's Docker socket, then talks to the Docker Engine API through it. On Windows, where OpenSSH can't take a C:\... socket path, dp forwards a random port on 127.0.0.1 instead; other users signed in to the same Windows machine could reach it while dp runs. Nothing is installed on the server. If the connection drops, dp starts a new tunnel in the background and the UI shows the connection state below the tabs; lists and open details refresh when it comes back, without losing your filters or selection.

Compose updates and edits over SSH need a POSIX shell and Compose v2 on the server, and key or agent authentication without prompts.

When something is slow

Run dp with a debug log and attach it to a bug report:

$ dp --debug-log ~/dp-debug.log

It records each Engine API request with its timing, the SSH tunnel starting and restarting with ssh's error output, and stats streams that retry. It doesn't record container environment, log lines or file contents. Host and container names do appear, so look it over before sharing.
